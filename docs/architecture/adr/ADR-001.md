## 1. Context

ASEP must execute long-running AI Code Review tasks while the Web API remains responsive for authentication, authorization, review status and user operations. Architecture must account for cancellation, bounded retries, concurrency, crash recovery and publication safety without imposing disproportionate operational complexity on a single developer maintaining a portfolio system.

## 2. Alternatives considered

| Criterion | A - Single-process modular monolith | B - Modular monolith + separate Worker | C - Microservices |
|---|---|---|---|
| Initial complexity | Low | Medium | High |
| Isolation of long-running jobs | Limited | Good | Good |
| Recovery/lifecycle boundary | Coupled to API | Clearer separation | Flexible but distributed |
| Testing complexity | Lower | Moderate | Higher |
| Operational overhead | Low | Moderate | High |
| Single-developer suitability | Good | Good | Less suitable |
| Future extensibility | Possible | Favorable | Possible at higher cost |

- **A:** Simplest deployment but long-running inference shares the API process lifecycle. API restart and inference resource contention complicate review isolation and recovery.
- **B:** A single backend codebase runs API and background Worker as distinct process roles. This improves independent lifecycle/recovery while preserving logical module boundaries.
- **C:** Independently deployed services provide scaling flexibility but introduce additional network, distributed transaction, tracing, authentication, deployment and test complexity without demonstrated M01 necessity.

## 3. Approved decision

**Choose option B: Modular Monolith with Separate Worker Processes.**

1. Maintain one backend codebase with explicit and testable logical modules.
2. API process handles HTTP, authentication/authorization and user-facing operations.
3. Worker process handles long-running Review and AI execution.
4. Processes use shared domain contracts and **durable workflow state**, not transient in-memory API request state.
5. API and Worker lifecycles are independent.
6. Microservices are **not** required for M01.
7. Review completion **does not** confer GitLab publication authority. Authorization, freshness and publication safety remain controlled at the Publication boundary.

## 4. Consequences and trade-offs

**Benefits**

- Prevent long-running inference from directly monopolizing the API lifecycle.
- Permit Worker restart/recovery independent of user-facing HTTP serving.
- Support explicit module contracts and meaningful integration testing.
- Retain an operable one-codebase architecture suitable for a personal project.

**Costs**

- Operate at least two process roles.
- Design durable job dispatch/state, graceful shutdown, cancellation, bounded retries and crash recovery.
- Coordinate shared persistence/ownership safely.

**Limits**

Separate processes do **not** automatically establish strong OS-level resource isolation, credential separation, persistence correctness or safe exactly-once execution. Those require concrete design and verification.
