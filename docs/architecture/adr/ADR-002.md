## 1. Context

ASEP M01 cần tự động phát hiện các GitLab Merge Request revisions, thực hiện AI Code Review bằng local inference và đăng feedback lên GitLab trong những điều kiện được phê duyệt.

Đây không phải một HTTP request/response workflow đơn giản.

Một Review có thể kéo dài, gặp model timeout, Worker restart, database failure hoặc GitLab API rate limits. Hệ thống cần tiếp tục vận hành mà không làm mất execution state hoặc tạo các tác động ngoài ý muốn.

Đặc biệt, GitLab publication là một external side effect. Khi GitLab nhận được request nhưng ASEP mất response, hệ thống không thể mặc định kết luận request thất bại.

Architecture cần giải quyết ba vấn đề:

1. Phát hiện MR revisions một cách đáng tin cậy.
2. Thực thi và phục hồi Review jobs với durable state.
3. Kiểm soát Publication để tránh duplicate, stale hoặc unauthorized GitLab writes.

## 2. Architectural Decision Drivers

Các yếu tố ảnh hưởng đến quyết định:

- M01 triển khai ban đầu trên môi trường self-hosted, localhost-only.
- MR Detection phải revision-aware.
- Long-running AI Review không phụ thuộc vòng đời HTTP requests.
- Review và Publication có trách nhiệm và quyền hạn khác nhau.
- Worker crashes và retries không được làm sai business state.
- Duplicate processing không được mặc định dẫn đến duplicate GitLab comments.
- Không tự động publish stale hoặc unauthorized content.
- Failed/partial external writes phải có trạng thái phục hồi.
- Minimal Persistence, retention và credential-security policies phải được giữ nguyên.
- Hạn chế distributed infrastructure complexity khi chưa có nhu cầu.

## 3. Decision 1 — Durable MR Detection & Revision-Aware Admission

**Status: APPROVED — 2026-10-17**

### 3.1. Alternatives Considered

| Alternative | Advantages | Limitations |
|---|---|---|
| GitLab Webhooks | Low-latency event delivery | Cần reachable ingress, delivery/retry validation |
| GitLab API Polling | Phù hợp localhost-only, dễ kiểm soát | Polling latency, API limits, pagination/recovery |
| In-memory Detection | Implementation đơn giản | Mất trạng thái khi restart, dễ duplicate/miss events |

### 3.2. Approved Decision

**Sử dụng GitLab API Polling + Revision-Aware Deduplication.**

Detection là một responsibility độc lập, chịu trách nhiệm:

- Poll các GitLab repositories/MRs được ASEP quản lý.
- Phát hiện thay đổi MR revisions.
- Xác định revision fingerprint.
- Thực hiện durable review admission.
- Duy trì durable checkpoint và reconciliation state.
- Tránh duplicate admission cho cùng revision.
- Hỗ trợ recovery sau restart.
- Không dựa hoàn toàn vào in-memory polling state.

Checkpoint handling phải xem xét pagination, overlapping polling windows, API errors và các trường hợp cần rescan.

Webhook có thể được bổ sung sau như một nguồn signal, nhưng không thay thế durable admission và revision deduplication.

### 3.3. Consequences

**Benefits:**

- Phù hợp với localhost-only M01.
- Không cần public webhook ingress.
- Có thể phát hiện thay đổi sau restart.
- Dễ xây dựng reproducible detection tests.

**Trade-offs:**

- Không bảo đảm realtime detection.
- Tiêu thụ GitLab API requests.
- Cần checkpoint và reconciliation logic.
- Polling sai có thể bỏ sót revisions hoặc tạo duplicate work.

**Deferred:**

- Polling interval.
- Exact checkpoint representation.
- Revision fingerprint implementation.
- Database schema.
- Queue/job library.
- Webhook integration.

## 4. Decision 2 — Durable Workflow Execution, Atomic Claim/Lease & Fencing

**Status: APPROVED — 2026-10-17**

### 4.1. Problem

Một Worker có thể crash hoặc mất kết nối trong lúc Review đang chạy.

Nếu chỉ dùng in-memory job state, ASEP không thể phân biệt chính xác job đã hoàn thành, đang chạy, bị treo hay cần recovery.

Ngoài ra, khi một Worker mất lease và Worker khác tiếp nhận job, Worker cũ vẫn có thể hoàn thành muộn.

Nếu không có concurrency protection, hai Workers có thể cùng ghi kết quả cho một operation.

### 4.2. Approved Decision

**Durable Workflow State + Atomic Claim/Lease + Fencing Token + Recovery Watchdog.**

Các nguyên tắc:

- Persist workflow state trước khi thực thi.
- Worker claim operation bằng atomic operation.
- Mỗi active claim có lease/ownership.
- Fencing token ngăn stale Workers commit kết quả sau khi mất quyền.
- Recovery Watchdog xác định các execution bị gián đoạn.
- Retry phải có budget và điều kiện an toàn.
- Cancellation và timeout phải được thể hiện trong durable state.
- Review completion không đồng nghĩa publication completion.

### 4.3. Logical State Model

Những trạng thái được thảo luận ở mức thiết kế:

| State | Meaning |
|---|---|
| `QUEUED` | Operation đang chờ execution |
| `RUNNING` | Worker đã claim và đang xử lý |
| `COMPLETED` | Execution hoàn thành hợp lệ |
| `RETRY_WAIT` | Chờ safe bounded retry |
| `RECOVERY_REQUIRED` | Cần phục hồi hoặc reconciliation |
| `CANCELLING` | Cancellation đã được yêu cầu |
| `FAILED` | Operation thất bại |
| `CANCELLED` | Operation kết thúc do cancellation |
| `SUPERSEDED` | Operation bị thay thế bởi revision/state mới khi policy yêu cầu |

Đây là logical state vocabulary được khôi phục từ các phiên review, không phải database enum/schema đã finalized.

### 4.4. Fencing Invariant

Giả sử:

- Worker A claim Review với fencing token 10.
- Worker A bị treo hoặc lease hết hạn.
- Worker B claim lại Review với fencing token 11.
- Worker A sau đó hoàn thành inference.

**Worker A không được commit kết quả bằng ownership đã hết hiệu lực.**

Việc kiểm tra phải xảy ra tại durable commit boundary, không chỉ ở một biến trong Worker memory.

### 4.5. Recovery & Retry

Recovery phải xử lý:

- Worker crash.
- Lease expiration.
- Lost heartbeat.
- Retryable execution failures.
- Cancellation.
- MR revision changes.
- Superseded work.
- Late completion từ stale Workers.

Một job được phép chạy lại khi cần recovery. Do đó architecture không tuyên bố exactly-once computation.

Mục tiêu là bảo vệ durable state và external side effects trước duplicate execution.

### 4.6. Consequences

**Benefits:**

- Recoverable long-running Review jobs.
- Hạn chế concurrent state corruption.
- Có thể kiểm chứng bằng PostgreSQL/concurrency tests.
- Phù hợp với separate Worker Processes của ADR-001.

**Costs:**

- Tăng transaction và state-machine complexity.
- Cần lease/heartbeat/recovery coordination.
- Phải kiểm thử fencing và stale completion.
- Retry không được triển khai như blind job replay.

**Deferred:**

- Exact lease duration.
- Retry intervals/budgets.
- Recovery Watchdog scheduling mechanism.
- Job library.
- Transaction/isolation implementation.
- Database/schema details.

## 5. Decision 3 — Durable Publication Ledger & Remote Reconciliation

**Status: APPROVED — 2026-10-17**

### 5.1. Problem

Publication tạo external GitLab effects.

Ví dụ:

1. ASEP gửi một request tạo inline discussion.
2. GitLab tạo discussion thành công.
3. Network connection bị gián đoạn trước khi ASEP nhận response.
4. Worker không biết comment đã tồn tại hay chưa.

Nếu ASEP retry ngay, GitLab có thể có hai discussions giống nhau.

Database transaction nội bộ không thể rollback một GitLab comment đã được tạo.

### 5.2. Approved Decision

**Durable Publication Ledger + Serialized Writes + Remote Reconciliation.**

Publication chịu trách nhiệm độc lập với Review execution.

Các nguyên tắc:

- Publication intent/state phải được ghi bền vững trước external write.
- Không cho phép concurrent Publication operations không kiểm soát trên cùng MR.
- Ghi nhận kết quả từng GitLab write.
- Phân biệt confirmed success với unknown outcome.
- Reconcile GitLab remote state trước retry đối với ambiguous writes.
- Không blind retry sau timeout hoặc lost response.
- Partial publication phải được ghi nhận chính xác.
- Publication phải kiểm tra current policy, authorization, revision freshness và content validity.
- Không đưa GitLab write credentials cho Review reasoning path.

### 5.3. Logical Publication States

| State | Meaning |
|---|---|
| `PLANNED` | Publication operation được ghi nhận |
| `WRITING` | Đang thực hiện external write |
| `PUBLISHED` | Đã xác nhận write thành công |
| `UNKNOWN` | Không xác định được remote outcome |
| `RECONCILIATION_REQUIRED` | Cần đối chiếu GitLab state |
| `FAILED` | Confirmed failed outcome |
| `BLOCKED` | Không đạt điều kiện publication |

Các trạng thái này thuộc logical design; exact transition rules và persisted schema vẫn deferred.

### 5.4. Publication Invariants

- Một current ASEP summary cho mỗi MR.
- Tối đa 3 selected inline findings theo approved publication scope.
- Inline findings phải có valid GitLab diff positions.
- Không automatic fallback từ invalid inline position sang general comments.
- Không tự resolve/delete historical inline discussions.
- GitLab comments phải qua controlled rendering và Quick Action protection.
- Không publish nội dung trái current authorization/policy.
- Không tự động approve hoặc merge MR.
- Không tuyên bố external exactly-once guarantees.

Sau khi CR-001 được phê duyệt, Publication còn phải hỗ trợ Shadow Mode và conditional Auto-Publish theo current Owner-enabled policy, với các independent quality/safety gates. Auto-Publish mặc định disabled.

### 5.5. Partial Publication & Ambiguous Responses

Nếu một hoặc nhiều inline comments được tạo thành công, nhưng các writes tiếp theo hoặc summary update thất bại:

- Không rollback giả những GitLab comments đã tồn tại.
- Ghi nhận confirmed per-write outcomes.
- Đánh dấu partial/unknown states phù hợp.
- Không tạo một summary mới chỉ vì request trước bị timeout.
- Reconcile bằng GitLab identifiers và remote state.
- Hiển thị accurate publication outcome cho Owner.

### 5.6. Consequences

**Benefits:**

- Hạn chế duplicate GitLab comments.
- Có durable evidence về publication attempts.
- Phân biệt Review success với Publication success.
- Hỗ trợ recovery và human inspection.
- Phù hợp human-governed publication policies.

**Costs:**

- Cần Publication Ledger và reconciliation mechanism.
- Tăng số lượng trạng thái/failure paths.
- Phải xử lý stale-write race conditions.
- Remote API có thể không hỗ trợ transactional/conditional writes đủ mạnh.

**Important limitation:**

GitLab không cung cấp một transaction chung giữa ASEP database và toàn bộ external comments.

Do đó, không được khẳng định absolute exactly-once publication hoặc zero-race stale-write prevention.

## 6. Durable Review → Publication Handoff

Review execution và Publication execution có boundaries khác nhau.

Một Review hoàn thành hợp lệ không được làm mất thông tin cần thiết để Publication tiếp nhận hoặc quyết định không publish.

Architecture yêu cầu:

- Durable handoff intent.
- Atomic consistency giữa Review completion và handoff state.
- Idempotent downstream admission.
- Publication kiểm tra policy tại execution boundary.
- Retry/recovery không được tự mở rộng quyền publication.

**Later technology direction — TSE-03:**

PostgreSQL-backed execution và Explicit PostgreSQL Outbox được chọn làm preferred implementation direction; db-scheduler là initial PoC candidate và JobRunr OSS là alternative.

Việc này bổ sung implementation direction sau ADR-002, không có nghĩa ADR-002 đã chốt một job library hoặc Outbox framework cụ thể.

## 7. Security & Data Lifecycle Constraints

ADR-002 phải tuân thủ những approved policies liên quan:

| Policy | Architectural implication |
|---|---|
| OPS-001 | Cleanup temporary data, kể cả crash leftovers |
| OPS-002 | Bounded safe retries và MR-version revalidation |
| OPS-003 | At most one active Review và one Publication operation trên mỗi MR |
| OPS-004 | Integration removal cancels jobs và removes pending data/credentials theo policy |
| SEC-009 | Restricted egress và no external AI inference/telemetry by default |
| RET-001..008 | Durable Review/Publication data tuân thủ retention và deletion |

Minimal Persistence vẫn áp dụng. Raw source, diffs và AI processing context không trở thành persistent cross-run caches chỉ vì hệ thống có durable job execution.

Publication Ledger chỉ giữ dữ liệu tối thiểu được phép theo approved retention policy.

## 8. Testing & Verification Obligations

ADR-002 cần được xác minh bằng automated integration, concurrency và fault-injection tests.

| Verification | Expected evidence |
|---|---|
| Duplicate MR detection | Không tạo duplicate active review admission |
| Poller restart | Durable checkpoint và rescan hoạt động đúng |
| Concurrent Worker claims | Atomic claim ngăn invalid concurrent ownership |
| Worker lease expiration | Recovery có thể tiếp nhận operation |
| Stale Worker completion | Fencing từ chối stale commit |
| Review completion/handoff | Durable handoff không bị mất sau crash |
| Duplicate handoff | Publication admission idempotent |
| GitLab timeout after write | Reconciliation thay vì blind retry |
| Partial publication | Ledger phản ánh actual confirmed/unknown outcomes |
| MR revision change | Stale writes bị chặn trong phạm vi có thể kiểm chứng |
| Integration removal | Pending work bị hủy/blocked theo approved policy |

Các obligations này chưa được xem là VERIFIED khi chỉ có architecture review.

## 9. Open Risks & Deferred Decisions

### Open Risks

- GitLab API capabilities và credential permissions.
- MR polling pagination/recovery correctness.
- Stale publication race conditions.
- Ambiguous GitLab write reconciliation.
- Duplicate comment prevention.
- Worker crash/retry/fencing correctness.
- Outbox handoff consistency.
- Publication Ledger expiration implications.
- Security/credential isolation.
- Temporary-data cleanup sau crash.

### Deferred Decisions

- Database schema và transaction design.
- Job/queue implementation library.
- Exact Outbox mechanism.
- Worker process topology.
- Lease duration và retry budgets.
- Recovery Watchdog implementation.
- Publication Ledger schema/reconciliation identifiers.
- GitLab API adaptation details.

Không tự biến bất kỳ hạng mục nào thành approved implementation decision.

## 11. Final Decision Summary

**ADR-002 lựa chọn một durable, revision-aware và recoverable workflow architecture.**

- MR Detection sử dụng GitLab API polling với durable checkpoints/deduplication.
- Review execution sử dụng atomic claim/lease, fencing và recovery.
- Review và Publication có boundaries độc lập.
- Publication sử dụng durable ledger, serialized operations và remote reconciliation.
- Không giả định exactly-once computation hay exactly-once external GitLab writes.
- Database/job/outbox implementation details được lựa chọn và kiểm chứng qua các technology/design tasks tiếp theo.
